## 바꾼 플레이

### ONBOARDING-1

**수정:** 초대장을 읽고 바로 ‘윤서와 인사하기’를 누르면 진행이 멈추던 문제를 재현해 수정했다. 숨겨진 초대장 대화의 클로즈업이 보행을 잠그고 있었고, 이를 해제한 뒤에도 경로 마지막 점의 허용 오차 때문에 대화 거리 밖에서 멈출 수 있었다. 화면에서 대화를 닫을 때 조사 카메라 잠금을 해제하고, 조사 접근 경로의 마지막 점은 생략하지 않도록 공통 처리를 수정했다.

기존 브라우저 드라이버의 `continueInspection()`은 수정 전 O00/exploring에서 시간 초과로 실패했다. 수정 후 새 게임과 저장 후 이어보기에서 윤서의 첫 대사를 확인했고, S01 진열장→모로→일정표의 직접 전환도 통과했다. 앞선 검증은 매번 ‘주변 살펴보기’를 먼저 눌러 이 경로를 놓쳤으므로, 드라이버의 일반 조사 진행도 주 버튼으로 직접 이어가도록 바꿨다. [수정 전후 기록](greeting-regression.json) · [윤서 대화 화면](browser/greeting-fixed.png). 통합 검사82/82, 최종 빌드30파일, 변경 코드 정적 검사 통과.

**개선:** 정적 프롤로그를 로비 이동→초대장 조사→윤서와 인사→전시실 안내 보행으로 바꿨다. 현재 목표·행동 이유·다음 행동을 보여 주며, 읽기 중단과 관찰 완료를 구분한다. 단서 대조와 퍼즐은 진행 단계에 맞는 주 버튼으로 열린다.

첫 사건은 진열장→모로와 흔적→일정표 순서다. 윤서의 부탁과 내일 9시 약속을 알고 첫 경로를 정한다. 첫 선택 A–D는 출발 결심만 보여 주며, 기존 결과 본문은 목적지 도착 뒤에 모두 읽는다. 지도 이동 중 미공개 대사나 단서를 노출하지 않는다. 모로도 진열장 조사 후 복도 쪽에서 걸어 나온다.

## 실제 브라우저 결과

- 로비 새 게임은 플레이어 `(0,19)`와 안내대/윤서가 있는 화면으로 즉시 시작했다. 목표 버튼으로 실제 접근한 뒤 초대장 조사가 열렸다.
- 초대장을 중단하면 미완료로 유지됐다. 두 번째 메시지에서 새로고침 후 같은 revision 4와 메시지 위치를 복원했다.
- 윤서에게 접근해 6개 메시지를 읽고 전시실로 출발했다. 시작 순간 윤서는 로비에 남아 보행했고, 플레이어는 로비→복도→전시실을 바닥 클릭으로 걸었다.
- 진열장 조사 전에는 모로와 후속 조사 대상이 숨겨졌다. 조사 뒤 모로가 남쪽 문에서 이동했다. [3초 움직임 영상](browser/onboarding-moro-arrival.webm)의 181개 관측 프레임 중 66프레임에서 이동했으며, z≈4.47에서 1.2로 이동했다.
- 세 관찰을 끝내면 ‘흔적을 대조하기’가 주 행동이 됐다. 잘못된 해석에는 설명이 나오고 결정 수는 0으로 유지됐다. 올바른 해석 뒤에는 경로 선택으로 이어졌다.

## 수정한 회귀

NPC 질문창의 빈 입력 상태에서 남은 aria-disabled가 글을 입력한 뒤에도 유지됐다. 실제 T22 질문으로 재현했고 `investigation-browser-driver.js`의 ask 검사가 수정 전 실패했다. 기본 disabled는 입력 조건, aria-disabled는 서버 처리 중 상태만 담당하게 바꿔 중복 상태를 제거했다. 같은 검사로 수정 후 실제 질문 제출·답변 표시까지 통과했다.

# 이전 읽기판의 구현과 리허설 이력

전체 원고를 상태머신에 연결하고, 실제 API를 쓰는 NPC 대화와 전체 화면 3D 게임 화면에서 주요 경로·모든 정의된 선택 분기를 실행했다. 외부 배포와 실제 참가자의 시간·재미 측정은 수행하지 않았다.

## 완성한 플레이

- 3장·21개 선택 장면·84개 행동·한 경로당 11회 결정·6개 엔딩.
- 메시지로 읽는 전체 원고. 내레이션·인물 대화·단서 문서·진행 안내·힌트를 구분하고 이전 대사는 기록창에서 읽는다.
- 팀별 진행, 자동 저장, 무결성 검사와 사건 재생을 통한 파일 복원, 결말 비교.

`artifacts/rehearsal-engine.json`은 독립 Python 명세와 20,988개 전이를 대조한 결과다. 실패 미션 여부로 같은 물리 상태를 중복 계산하지 않아 기존 설계 검사와 상태 수가 다르다. [브라우저 결과](rehearsal-browser.json)는 146개 사례를 기록한다. 전체 4^11 조합이나 무한히 가능한 AI 질문을 모두 검증했다는 뜻은 아니다.

배포용 `dist/`도 별도 Node 서버(5189)에서 열었다. 공식 시정 경로는 E3(배 손상·원본 보존·모로 작동·배터리 소비), 모로 인계 경로는 E5(배/원본 보존·모로 방전·배터리 소비)로 끝까지 읽었다. 팀별 결말 비교에서도 이 차이가 유지됐다.

## 도구 검사

- `npm test`: **75/75 통과**, 약 0.27초. 기존 T22와 전체 경로, API 경계, 저장·복원, 세션 격리, 취소·지연 응답을 합쳐 검사했다.
- `npm run build`: **24개 배포 파일 생성 성공**. 실행 JS 구문 검사 포함. `.env`·세션 파일·실제 설정 키가 빌드에 포함되지 않았음을 검사했다.
- `npm run rehearse`: **84선택 / 89목적지 분기 / 146조건 사례 / 6엔딩 통과**.
- ESLint 8.43.0: 미정의/미사용 변수·도달 불가능 코드·중복 키·typeof 검사, 경고 0.
- 기존 환경의 Prettier 2.8.8로 새 구현 파일을 정리했다. 런타임 의존성은 Three.js 0.186.1 하나다.
- 이 프로젝트는 JavaScript이며 별도 TypeScript 정적 타입 검사 설정은 없다. 구문 검사와 실행 경계 검증을 TypeScript 검사라고 표시하지 않는다.

같은 검사를 파일마다 반복하지 않았다. 첫 엔진 검사 후 통합 시 한 차례 전체 검사했고, 이후 원고나 선택 규칙을 변경하지 않은 시각 조정은 해당 화면·동작만 확인했다.

## 실제 AI와 실패 경계

설정된 게이트웨이에서 Decisions와 Responses를 모두 실제 호출했다. 모로·윤서·나래의 정상 대화, 수신 확인 추궁, 오탈자, 닳은 열쇠의 불충분한 근거, 부정·인용 정정을 확인했다. 상세 호출 결과와 오판 보완은 [AI 연결 기록](../docs/narrative/ai-integration.md)에 있다.

모바일 브라우저의 T22에서 직접 질문을 제출해 `AI_RESOLVE / challenge / supported`를 받았으며, 윤서의 작성된 인정문 뒤 실제 새 문장이 표시됐다. `request_received`와 `return_delayed`만 공개되고 `statement`는 false로 유지됐다. AI 대사 검증은 환각을 완전히 보장하지 않으며, 모델 문장과 상태 전이는 분리되어 있다.

거부·429·네트워크·잘못된 출력·위조 근거·취소·기한·늦은 응답은 API 경계 대체를 통한 18개 통합 검사와 HTTP 세션 검사로 확인했다. 실제 서비스 장애를 일부러 발생시키지는 않았다.

## 발견해 수정한 문제

- **UI-1:** 기록창에서 →를 누르면 뒤쪽 본편이 진행됐다. 실제 브라우저에서 revision 0→1로 재현한 뒤 열린 dialog에서는 진행 단축키를 막았다. 같은 조건을 다시 실행해 revision 4→4로 유지됨을 확인했다.
- 밝은 공간 위의 목표/시작 문구가 흐려 보여 별도 어두운 배경을 넣었다.
- `안내`와 문서 발췌가 인물 대사처럼 보이던 것을 공통 분류로 고쳤다.
- **AI-1:** 요청서를 보유했다는 이유만으로 닳은 열쇠 추궁을 인정하던 오판을 실제 호출에서 발견했다. 질문이 실제 사용하는 근거를 분리 판정하고 회귀 사례로 남겼다.
