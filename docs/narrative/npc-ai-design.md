# NPC 대화와 단서 추궁 설계 v0.1

> 과거 설계 기록입니다. 현재 버전은 AI 연결을 제거하고 작성된 질문·대사·선택을 사용하는 정적 게임입니다. 아래 내용은 이전 기획의 기록이며 현재 실행 계약이 아닙니다. 실행 방법은 [README](../../README.md)를 따릅니다.

플레이어가 장면 속 인물에게 직접 질문하고, 확보한 단서로 말의 모순을 짚으면 인물의 답변과 행동이 바뀐다. OpenAI Responses API는 NPC 대화를 만들고, Decisions API는 질문·추궁의 의미를 판정한다.

**사용자가 정한 방향:** NPC에 AI Agent를 부여한 대화, Decisions API를 활용한 단서 추궁. 충분한 대사를 메시지로 읽으며 진행하고 음성은 요구하지 않는다. 첫 버전은 텍스트 입력과 메시지 표시로 구성하며 GPT-Live는 사용하지 않는다. T22의 상태 전이와 작성 대사 매핑은 구현했다. 실제 API 연결과 유료 호출은 하지 않았다.

## 1. 플레이 흐름

장면을 본다 → 인물에게 질문한다 → 단서를 골라 제시하며 추궁한다 → 인물이 반응한다 → 팀이 A~D 행동을 하나 확정한다 → 결과 장면과 다음 루트로 이동한다.

대화는 장면 내부에서 진행한다. 중요한 행동과 이동은 여전히 네 선택으로 확정한다. 자유 대화 중 “배터리를 주세요”라고 말한 것은 요청이며, 팀의 획득 행동까지 자동으로 실행한 것은 아니다. 해당 선택지를 강조하고 확정을 기다린다.

팀이 함께 질문을 정하고 대표 한 명이 입력한다. 제안 질문을 눌러 시작할 수도 있다. 문장의 유창함이나 말투를 점수로 매기지 않는다. 핵심은 관찰한 사실과 주장의 관계다.

### 대사 분량과 메시지 구성

대화는 **사건을 전달하는 작성 원고 + 더 알아보는 선택 화제 + 플레이어의 자유 질문**으로 구성한다. AI가 없는 조사 장면도 인물의 메시지와 짧은 서술로 충분히 읽을 수 있게 쓴다. 대화가 가능한 장면과 API를 호출하는 장면은 같은 범위가 아니다.

일반 조사 장면은 8~14개, 주요 대면은 25~40개 메시지에 선택 후 반응을 더하는 분량을 원고 작성의 출발점으로 제안한다. 이는 모든 팀이 반드시 읽어야 하는 할당량이나 실제 소요 시간의 측정값이 아니다. 각 대화 묶음은 새로운 관찰·주장·해명·동기·행동 결과 중 하나를 추가해야 한다. 같은 사실을 반복하는 문장은 수를 채우려고 남기지 않는다.

한 메시지는 보통 1~3문장으로 읽기 쉽게 나누고, 인물의 행동은 별도 짧은 서술로 표시한다. 앞선 대화와 선택한 단서를 함께 다시 볼 수 있게 한다. 자동 넘김이나 타이핑 대기를 강제하지 않는다. 장면이 길어져도 사용자가 원하면 행동 선택으로 갈 수 있다.

메시지 하나가 API 호출 하나라는 뜻은 아니다. 작성 대사는 API 없이 읽고, 자유 질문 한 턴의 응답은 여러 메시지로 나눠 보여줄 수 있다. 한 턴에 보내는 생성 요청과 플레이어가 읽는 말풍선 수를 따로 센다.

## 2. NPC마다 다른 역할

| NPC | 태도와 대화 목적 | 아는 것 | 말하지 못하거나 아직 드러내지 않는 것 | 주된 재미 |
| --- | --- | --- | --- | --- |
| 모로 | 짧고 정확하게 작업을 설명한다. 필요하면 질문의 전제를 바로잡는다. | 자신의 이송 기록, 반환 요청 처리, 장치 상태 | 윤서의 속마음, 아직 보지 않은 팀의 경로, 최종 엔딩 | ‘훔쳤다’와 ‘옮겼다’의 차이를 캐묻고 로그의 의미를 발견한다. |
| 윤서 | 처음에는 방어적이다. 자신의 책임과 박물관을 잃는 두려움을 구분하지 못한다. | 규약을 바꾼 사실, 요청을 받은 사실, 시설 방치 | 현재 공개 단계보다 앞선 고백은 아직 하지 않는다. | 실제 증거를 제시해 이미 한 말을 수정하게 한다. |
| 나래 | 자신의 뜻과 물건 처리에 필요한 사실을 명확히 설명한다. | 원래 약속, 반환 요청, 수령 방법 | 직접 보지 않은 박물관 내부 사건 | 플레이어가 배의 상태를 설명하면 그 결과에 맞게 대화가 달라진다. |

‘NPC Agent’는 인물별 성격·지식·목표·대화 기억을 가진 역할이다. NPC들이 서로 자율 호출하는 시스템을 뜻하지 않는다. 팀별/NPC별 대화는 분리하며 게임 상태와 사건의 진실은 한 곳에서 관리한다.

## 3. 적용할 장면

| 장면 | 대화에서 하는 일 | 대화 이후의 기존 행동 |
| --- | --- | --- |
| T21 모로 대면 | 누가 요청했는지, 어떤 규약을 따랐는지, 왜 젖은 종이를 들고 있는지 묻는다. | 로그/요청 자료 보존 또는 배터리/도면 확보 중 하나 확정 |
| T22 윤서 대면 | 윤서가 실제로 말한 주장과 소유한 자료를 대조해 해명·인정을 끌어낸다. | 서명 진술/요청서/배터리/도면 중 하나 확정 |
| S31 나래 연락 | 구조 결과를 알리고 원래 약속의 뜻을 확인한다. | 반환/공식 시정/모로 이동/현장 인계 중 방향 확정 |

한 경로에는 T21 또는 T22 중 하나와 S31이 포함되므로, 초기 제안은 팀당 최대 두 **AI 자유 대화 장면**이다. 나머지 장면에도 작성된 대사가 들어간다. 앞서 제안한 장면당 자유 질문 3회는 API 리허설용 상한이며 전체 대화를 세 번만 주고받는다는 뜻이 아니다. 확정값이 아니고, 자유 질문을 소진해도 작성된 화제와 4지선다로 진행할 수 있다.

첫 검토용 사례는 **T22 윤서 대면**으로 집중한다. 이 장면의 추궁이 재미있는지 확인한 뒤 모로와 나래에 같은 형식을 적용한다.

## 4. T22 실제 플레이 예시

### 입장 조건

팀은 I03-C의 접수 단말에서 `request`를 확보했다. 자료에는 전날의 반환 요청과 윤서의 수신 확인이 있다. S12에서 윤서가 반환실 열쇠를 꺼내는 모습도 봤다. 아직 윤서에게 요청 수신을 인정받지는 않은 경로다.

I04를 거친 팀에는 아래의 ‘받은 적 없다’는 대사를 사용하지 않는다. I04에서 윤서는 이미 요청 수신을 인정했으므로, ‘받은 요청을 왜 처리하지 않았는가’로 질문이 이어진다. 이 공개 이력은 요청서 보유 여부와 별개다. I04-C/D처럼 장비를 골랐어도 이미 들은 인정을 취소하지 않는다.

### 장면과 대화

아래는 API 판정이 들어가는 접점의 요약이다. 탐색 질문, 회피, 인정 후 추가 대화까지 읽는 원고는 [T22 메시지 콘티](t22-storyboard.md)에 있다.

1. 윤서가 요청서가 보이는 쪽을 피하며 말한다. **“돌려달라는 연락은 받은 적 없어요. 모로가 혼자 움직인 거예요.”** 이 문장은 이 장면에 허용한 방어적 주장이다. 모델이 새 알리바이를 지어내지는 않는다.
2. 팀이 기록장에서 **‘반환 요청서’**를 선택하고 입력한다. **“어제 접수된 요청서에 관장님 수신 확인이 찍혀 있는데, 왜 못 받았다고 하세요?”**
3. 서버가 실제 `request` 보유와 현재 주장 ID를 확인한다. Decisions는 입력이 수신 확인을 근거로 ‘못 받았다’는 주장을 반박하는지 판단한다.
4. 근거 있는 추궁으로 받아들여지면 윤서가 요청서를 바라보고 말을 멈춘다. **“받았어요. 내일 배를 띄우고 싶다고… 적혀 있었죠. 제가 모른 척한 겁니다.”** 이 답변의 핵심 사실은 작가가 정한 공개 문장이다. Responses는 그 사실 안에서 말투와 이어지는 응답을 만든다.
5. 기록장에 **‘윤서가 요청 수신을 인정함 — 구두 진술’**이 남는다. 아직 `statement=true`는 아니다.
6. 팀은 A ‘인정한 사실을 서명으로 남기게 한다’를 고를지, 다른 자료나 장비를 확보할지 결정한다. A를 확정한 경우에만 서명된 증거를 얻는다.

이는 제안한 대화 예시이며 실제 모델 실행 결과가 아니다.

### 같은 질문도 증거에 따라 다른 반응

| 플레이어의 행동 | 판정과 NPC 반응 | 게임 결과 |
| --- | --- | --- |
| 소유한 요청서를 제시하며 수신 확인을 지적 | 구체적 모순을 짚은 추궁. 요청을 받은 사실을 인정한다. | 구두 인정 공개, 표정·동작 변화, 서명 요청 행동의 문맥 변화 |
| “열쇠가 닳았으니 어제도 쓴 거죠?” | 의심의 근거는 되지만 최근 사용의 증거는 아니다. “오래 사용한 열쇠예요”라는 해명을 들을 수 있다. | 새 증거나 자동 자백 없음. 다른 사실을 질문 가능 |
| 보유하지 않은 요청서를 “가지고 있다”고 말함 | 서버상 보유 자료가 아니므로 증거 제출로 처리하지 않는다. | 질문 자체에는 답할 수 있지만 문서 확인 효과 없음 |
| “일단 다 인정하고 서명해요” | 행동 요청으로 분류한다. 증거 추궁에 성공했다고 기록하지 않는다. | 서명 요청 선택지를 안내하고 팀 확정을 기다림 |
| “요청서를 못 받았다는 게 아니라, 받았다고 말한 거죠?” | 앞선 말의 정정·인용 여부를 문맥으로 확인한다. 단순 키워드 포함만으로 성공하지 않는다. | 모호하면 짧게 확인하고 상태 유지 |

## 5. 추궁 가능한 주장과 증거

아래 주장은 T22에서 작가가 허용하는 후보다. 매번 모두 말하게 하지는 않는다. 이미 인정한 사실과 모순되는 후보는 제거한다. 앞선 대화·장면에서 인정한 사실을 다시 부정하지 않는다.

| 주장 ID | 윤서의 방어적 주장 | 실제 보유가 필요한 반박 자료 | 인정 후 공개할 사실 |
| --- | --- | --- | --- |
| no_request | “돌려달라는 요청을 받은 적 없어요.” | request | 요청을 읽고도 반환을 미뤘다. |
| permanent_donation | “처음부터 영구 기증을 받는 곳이었어요.” | charter | 원래 규약에는 반환 조항이 있었다. |
| moro_without_rule | “모로가 규칙도 없이 멋대로 옮겼어요.” | log | 모로의 이동은 옛 반환 규약에 근거했다. |

제시 가능한 증거가 없는 팀도 대화할 수 있다. 현재 관찰을 바탕으로 질문하고, 정해진 ‘기록 대조’ 안내를 이용하거나 다음 4지선다를 확정한다. 추궁 실패 때문에 필수 진실이나 엔딩으로 가는 길을 막지 않는다. 핵심 진실은 S22에서 모든 팀에게 전달된다.

T22-A는 **윤서와 접수 단말의 요청 원문·옛 반환 조항·변경된 안내를 함께 대조하는 고정 장면 → 규약을 안내에서 빼고 요청을 미룬 사실 인정 → 서명**으로 진행한다. 이미 인정한 부분은 짧게 확인하고 넘어간다. ‘요청을 받았다’는 인정만으로 규약 변경까지 입증했다고 처리하지 않는다. 이 행동은 한 번의 자원/정보 확보 선택을 소비하며, 화면에서 함께 읽은 문서가 모두 소지품에 추가되는 것은 아니다. 확보하는 것은 해당 사실이 명시된 서명 진술 하나다.

## 6. API 역할 분담

| 담당 | 맡는 일 | 맡기지 않는 일 |
| --- | --- | --- |
| Responses API | 인물의 말투·기억·공개 가능한 사실에 맞춰 질문에 답하고 짧은 대사를 생성 | 사건의 진실, 새로운 알리바이, 임의의 아이템·엔딩 생성 |
| Decisions API | 발화 의도 분류, 주어진 증거와 주장 사이의 모순 지적 여부 판단 | 긴 NPC 대사 생성, 실제 소지품 보유 여부 결정, 상태 직접 변경 |
| 게임 규칙 | 증거 보유·장면 조건·공개 단계 확인, 구두 인정 기록, 확정된 A~D 실행 | 플레이어 문장의 의미를 고정 키워드만으로 판단 |
| Three.js/화면 | 정해 둔 시선·자세·짧은 동작, 대사·증거·기록·선택 표시 | API 결과만으로 임의의 애니메이션이나 공간을 즉석 제작 |

Decisions의 `choice`는 발화 의도를 미리 정의한 범주에서 고르는 데, `predicate`는 특정 주장에 대한 근거 있는 반박인지 평가하는 데 쓴다. `score`는 지원되지만 첫 버전에는 참가자 점수나 설득력 점수로 쓰지 않는다.

서로 독립적인 의도와 반박 여부 질문은 한 Decisions 요청에 함께 넣을 수 있다. 조건부 후속 판정이 필요하면 앞선 결과를 확인한 뒤 별도로 수행한다. 확률·신뢰도는 추정값이며 정답 보증이 아니다. 승인 임계값은 예제 발화를 평가한 뒤 정하고 임의의 숫자를 확정하지 않는다.

## 7. 대화 한 턴의 계약

입력은 현재 팀·장면·NPC·장면 버전, 플레이어 문장, 선택한 증거 ID다. 실제 증거 내용·보유 여부·현재 NPC 주장·이미 공개한 사실은 서버 상태에서 읽는다. 플레이어가 보낸 JSON이나 문장으로 이를 덮어쓰지 않는다.

1. 현재 장면에서 대화가 가능한지와 요청 길이·횟수를 확인한다.
2. 선택한 증거가 해당 팀의 기록에 있는지 검사한다.
3. Decisions에 관찰 가능한 기준과 실제 자료를 보내 의미를 판정한다.
4. 게임 규칙이 공개 가능한 인정/해명/재질문 중 하나를 확정한다.
5. Responses에 현재 허용된 사실과 반응만 전달해 NPC 대사를 만든다. 이 장면에서 숨겨야 하는 후반 반전·엔딩 원고는 전달하지 않는다.
6. 대사와 사실 ID, 허용된 동작 ID를 검증하고 화면에 표시한다. 핵심 인정 문장은 승인된 사실 문구와 함께 보여준다.
7. 팀이 A~D를 확정해야만 물건·서명·장면 이동을 적용한다.

문장이 자연스럽게 생성된다는 것과 사실이 항상 맞는다는 것은 다르다. 허용 사실만 제공하고 형식을 검증해도 대사 모순을 완전히 보증할 수 없으므로, 실제 모델 평가와 고정 대사 대체가 필요하다.

읽기·질문·대기·취소·확정의 상태와 ID/조건에 따른 매핑은 [상태·사건·시나리오 계약](game-state-design.md)에 정의한다. AI 해석 후보와 실제 상태 변경을 구분하며, 재생 시에는 확정된 사건과 대사를 사용한다.

## 8. 실패·중복·모호함

| 상황 | 처리 |
| --- | --- |
| 추궁 근거가 약하거나 판정이 모호함 | 새 사실을 확정하지 않고 NPC가 짧게 확인 질문. 실패 벌점은 없음. 이미 전송한 API 요청은 호출 상한에 포함하며, 이후 고정 질문으로도 진행 가능. |
| 서버가 가진 자료와 플레이어 주장 불일치 | 보유하지 않은 증거로 인정하지 않음. 실제 기록을 선택하도록 안내. |
| API 타임아웃·한도·거절·형식 오류 | 해당 장면의 고정 질문과 대사로 계속 진행. 아이템·루트 상태 유지. |
| 장면 이동 후 늦은 응답 도착 | 팀·장면 버전이 맞지 않으면 적용하지 않음. |
| 중복 전송·같은 추궁 반복 | 같은 요청은 한 번만 반영. 이미 인정한 사실을 다시 보상하거나 부정하지 않음. |
| 대화 중 배터리 획득·서명·이동 요청 | 해당 A~D 행동을 제안하고 확정 대기. 대화만으로 실행하지 않음. |
| 모로가 잠든 상태 | 작동하는 NPC로 대화하지 않음. 이미 저장한 기록만 읽거나 정해진 배터리 사용 행동을 선택. |
| 종료한 모험에 입력 | 새로운 게임 상태를 만들지 않고 완료된 기록을 보여줌. |
| 팀 세 곳에서 동시에 대화 | 팀별 상태·NPC 기억을 분리. 다른 팀이 얻은 단서를 섞지 않음. |

## 9. 기존 루트와 시간·비용 영향

- 현재 21개 선택 장면·84개 행동·11회 결정의 이동표는 유지한다. 대화 구간은 장면 내부의 새로운 세부 흐름이다.
- `statement`, `log`, `request` 같은 진행 자산은 기존 A~D 확정으로만 얻는다. 구두 인정은 별도 대화 기록이며 기존 엔딩 조건의 증거를 자동 대체하지 않는다.
- 그러므로 이전 루트 검사의 결과는 핵심 이동표에 대해 재사용할 수 있지만, AI 대화 상태·응답 품질·지연·비용을 검증한 결과는 아니다.
- 55분을 그대로 유지한다고 가정하지 않는다. 자유 대화 시간을 기존 장면 시간 안에 포함할지 실제 리허설로 조정한다. 대화 횟수를 늘리고 총시간은 그대로라고 주장하지 않는다.
- 팀당 최대2장면 × 장면당3개 자유 질문 × 3팀이면 최대18개 자유 대화 턴이다. 턴마다 Decisions 1회와 Responses 1회를 쓴다는 가정에서는 각각18회다. 재시도·추가 검증·시스템 도입 대사는 별도다.
- 리허설 초안에서는 서버가 접수해 외부로 전송한 턴을 상한에 포함한다. 모호한 판정이나 통신 오류도 자동으로 무제한 재시도하지 않는다. 고정 질문 버튼은 미리 작성한 응답을 사용해 추가 호출 없이 진행한다. 입력 검증에서 거부한 문장과 중복 전송은 새 턴으로 세지 않는다.
- API는 사용량에 따라 과금된다. 초기 ‘추가 비용0원’ 조건은 API 예산 또는 사용 가능한 크레딧 범위를 정하면서 다시 확인해야 한다. 지금은 고정 판정 예제로 T22를 실행했으며 유료 호출은 하지 않았다.
- API 키는 서버에서 보관한다. 웹에 연결되는 최소 서버 기능이 필요하므로 기존 완전 오프라인 구상은 AI 기능에 그대로 적용되지 않는다. 연결이 없어도 고정 대사로 플레이할 수 있는 경로를 마련한다.

## 10. 구현 전에 보여줄 다음 결과

콘티 검토 후 승인된 T22 상태머신을 구현했다. [실행한 메시지 기록](../../artifacts/t22-demo.md)은 **도입 → 질문 → 증거 추궁 → 인정 → 추가 대화 → A 확정 → D21 인계**를 실제 전이 함수로 생성한 결과다. 화면과 실제 모델 연결은 후속 단계다.

모델 검증에는 다음 사례를 포함한다: 같은 추궁의 다른 표현, 오탈자, 짧은 문장, 부정문, 인용, 이미 인정한 사실, 잘못 고른 자료, 소유하지 않은 자료, 키워드만 포함한 무관한 말, 역할 변경 요구, 늦게 도착한 응답, 다른 팀의 단서 혼입. 아직 이 테스트를 실행하지 않았다.

## 공식 문서 확인

2026-10-27 공식 문서 확인 기준:

- [Decisions API](https://developers.openai.com/api/docs/guides/decisions): 텍스트·이미지·JSON을 받아 predicate/choice/score를 반환한다. 현재 POST /v1/decisions와 gpt-6-luna를 사용한다. 답변의 해석과 행동 실행은 애플리케이션이 맡는다.
- [Function calling](https://developers.openai.com/api/docs/guides/function-calling): Responses API와 애플리케이션의 데이터·행동 연결. NPC를 구성한다고 별도 제품인 ‘NPC Agent API’가 생기는 것은 아니다.
- [API 가격](https://developers.openai.com/api/docs/pricing) 및 Decisions 가이드의 가격 항목: Decisions의 gpt-6-luna 비캐시 입력은 100만 토큰당 $0.10, 출력 토큰은 별도 청구하지 않는다고 안내한다. Responses 대화 생성 비용은 별도이며 실제 비용은 모델과 사용량으로 산정한다.

GPT-Live 통합은 사용 범위에서 제외했다. Decisions와 Responses를 서버에서 직접 호출하는 설계다.
